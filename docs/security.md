# Security and privacy

**Webhook payloads may contain confidential or personal data**: customer
details, addresses, order contents, and tokens a provider includes. Treat
RelayLab like the systems that send to it. This page summarises how RelayLab
handles that data; each section links to the detailed page.

## What is stored

For each request an endpoint receives: the method, path, query, headers, the
body exactly as sent (bytes, not text), the content type, the time, the user
agent, and the sender's network truncated to a /24 (IPv4) or /48 (IPv6)
range. Full client IP addresses are not stored with events. Session rows
store no IP address or user agent. The only full IP addresses kept are Better
Auth's rate-limit counters, which are deleted once their window has passed.

Details: [Received events](security/events.md),
[Data retention and deletion](security/data-retention.md#what-is-stored).

## Credentials are removed on arrival

Before anything is stored, a central redactor replaces the values of
credential headers (`Authorization`, `Cookie`, `Proxy-Authorization`, API key
headers, and names containing `token`, `secret`, `signature`, and similar) and
of credential query parameters with `[REDACTED]`. The original value is never
written to the database or to logs and cannot be revealed later; the UI shows
"Removed at receipt". Operators can add names with
`INGEST_REDACT_EXTRA_HEADERS` and `INGEST_REDACT_EXTRA_PARAMS`; built-in
names cannot be removed.

Received content is never rendered as HTML: bodies are shown as text, a JSON
tree, or hex, and the raw download is served as an inert attachment.

Details: [Received events](security/events.md).

## Secrets

- **Endpoint URLs** are credentials. Tokens are stored as an HMAC lookup hash
  plus an AES-256-GCM ciphertext; rotate an endpoint's URL if it leaks.
- **Header values added to a replay** are stored encrypted (AES-256-GCM, a
  separate key) and erased as soon as the replay finishes.
- **Sessions** are signed cookies (`HttpOnly`, `SameSite=Lax`, `Secure` and
  `__Secure-` prefixed in production); passwords are scrypt hashes held only
  by the auth service.
- **Configuration secrets** come from the environment (Secret Manager in
  production) and are never logged: configuration errors name the variable,
  never its value.
- **Logs** never contain bodies, credential header values, session tokens,
  or endpoint tokens; request logs record route patterns, not raw paths.

Details: [Authentication architecture](architecture/auth.md),
[Deployment: secrets](deployment.md#secrets).

## Retention and deletion

Events and their replays are deleted after the retention period (7 days by
default, 24 hours on a public demo) and beyond a per-project cap. Owners can
delete one event, all events of an endpoint, an endpoint, a project, or
their account; deletion is permanent and cascades. Demo workspaces are
deleted after 24 hours.

Details: [Data retention and deletion](security/data-retention.md).

## Replay restrictions

Replaying to a URL is the one place RelayLab sends requests on a user's
behalf, so it is guarded against server-side request forgery:

- HTTPS only (plain HTTP only behind a development flag), allowed ports only.
- Every DNS answer and the actual socket address must be a public address:
  loopback, private, link-local, multicast, reserved ranges, and cloud
  metadata addresses are refused, including through alternate IP spellings
  and DNS rebinding. RelayLab's own hosts and internal names are refused.
- Redirects are never followed; strict connect, header, and total timeouts;
  response size and concurrency caps.
- Signature and credential headers from the original request are not
  forwarded; users add headers explicitly.
- URL replay is off by default in production (`REPLAY_ENABLED`). Replay to the
  built-in test sink never opens a network connection and is always
  available. Demo users can only replay to their test sink.

Every item of the brief's SSRF checklist maps to a test.

Details: [Outbound requests and SSRF protections](security/outbound-replay.md).

## Isolation between users

Every dashboard query is scoped to the signed-in user; another user's
project, endpoint, event, or replay is indistinguishable from one that does
not exist (`404`). The acting user comes only from the validated session,
never from the request. The Go runtime database role can only read the auth
tables it needs.

Details: [Authentication architecture](architecture/auth.md).

## What RelayLab does not do

It does not use payloads for analytics or model training, does not forward
received credentials, and does not render received HTML or scripts.
